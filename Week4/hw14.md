- what is thread state

  New → Runnable (start()); scheduler runs it; leaves Runnable into Blocked (waiting for a lock), Waiting (wait/join, no timeout), or Timed Waiting (sleep/timed wait); each returns to Runnable; run() completes → Terminated. (Java doesn't expose "Running" separately — it's part of Runnable.)

- what is thread local

  Each thread gets its own isolated copy of a variable, so no shared state to synchronize. Memory-leak risk: in a thread pool, threads are reused; if you set() and never remove(), the value stays attached to the pooled thread. Always call remove() in a finally block.

- how to send request from angular to backend

  In Angular I use the HttpClient service. I inject it into a service class — keeping HTTP out of the component — and call get, post, put, or delete with the backend URL, attaching headers, query params, or a JSON body as needed. It returns an RxJS Observable, so I either subscribe to it or convert it with firstValueFrom and await it.
  
  Two things I always handle. First, CORS — that's a backend concern. Since the Angular app and the API are on different origins, the browser blocks the call unless the server allows it, so on the Spring Boot side I configure CORS with @CrossOrigin or a global config to whitelist the frontend's origin. Second, the response is asynchronous — the call is non-blocking by default and runs off the main thread, so I'm just choosing whether to consume it via subscribe or async/await. And I handle errors either in the subscribe callback or with a centralized HttpInterceptor.

### Q&A

- what is index

  Index is a separate data structure that lets the database locate rows without scanning the whole table. 

  Pros: faster reads; Cons: extra storage and slower writes.

  Without index, a WHERE or JOIN on a column takes O(n). With index, the lookup drops to roughly O(logn) because the index keeps the column in a structure (usually a B+ tree) with  pointers back to the rows. The cost is that every insert, update, or delete has to maintain the index too, and if a write breaks the tree's structure it forces a rebuild — so writes slow down.

- clustered index vs nonclustered index

   A clustered index defines the physical order of the rows on disk, so a table can only have one. A non-clustered (secondary) index is a separate structure whose leaves hold the indexed key plus a pointer back to the row, so you can have many of them. 

- data structure for index
  
  The default is a B+ tree, because it handles both equality and range queries well while staying balanced. All the values sit in the leaf nodes and the leaves are linked together, so range scans, ORDER BY, and prefix matches walk the leaves efficiently, and the low tree height means few disk reads. A plain B-tree also stores data in internal nodes, which makes range scans worse — that's why databases use B+ rather than B. Beyond that there are specialized structures: a hash index gives O(1) equality lookups but can't do ranges or ordering; a bitmap index suits low-cardinality columns like status or gender, mostly in analytics; and R-tree / GiST handle spatial data while inverted indexes handle full-text search. 

- view vs store procedure

  View is a virtual table representing a saved `SELECT` query used to simplify data reading.

  Stored Procedure is an executable script containing advanced logic, parameters, and multiple database commands to perform actions like modifications or validations. Eg. `EXEC ProcedureName`

- view vs material view

  A regular view stores only the query definition and re-runs it every time you access it, so it's always current but pays the full computation cost on each read. 
  
  A materialized view physically stores the result set on disk, so reads are fast because nothing is recomputed — but the data can be stale until you refresh it. 

- how to tune the sql query

  Use `EXPLAIN` OR `EXPLAIN ANALYZE` to get the root-cause and execution plan. After understanding the cause, we can:

  1. Add an index
  2. Do not SELECT all. Select exact fields
  3. Remove unnecessary joins
  4. Use UNION ALL instead of UNION
  5. Use JOIN ON instead of WHERE to join tables
  6. Use LIMIT to do pagination 
  7. Create View or stored procedure to improve performance
  8. Avoid using IN.

- Saga vs 2PC 

  They are both architectural patterns for managing distributed transactions.

  2PC (2-phase commit) uses a central coordinator to ensure that all services either commit or roll back a transaction as a single unit. Strict consistency & indivisible atomicity, but if the coordinator crashes during the commit phase, database locks are held hostage so can have high latency due to locking.

  Saga: A Saga breaks a large distributed transaction into a sequence of smaller, independent local transactions. Highly scalable, resilient and non-blocking, but more complex to implement because steps execute independently, users might see temporary inconsistent data before the sage completes.
