## Q&A
- what are the use case for the following design pattern in Banking, E-Commerce and Health Insurance Industry (Total 12 use cases, recommend to do some research)
  - singleton:  one shared instance, lifecycle-managed, loaded once and reused. in springboot, beans are singleton-scoped by default.
    - Banking: a centralized configuration/connection-pool manager holding currency/exchange rates. DB connection pool for the core ledger (loaded once at startup and shared read-only acroos all transaction-processing threads)
    - E-commerce: A single in-memory cache for the hot product catalog or a shared Redis connection pool for shopping carts 
    - Health Insurance:  A single eligibility/benefits rules engine that loads plan rules once and serves every claim-adjudication request, avoiding repeated expensive rule-set loading
  - factory: encapsulates object creation and returns different concrete types based on input, so the caller doesn't depend on concrete classes. Best for "given type X, build object Y."
    - Banking: A PaymentProcessorFactory that returns the right processor by payment type — ACH, wire, SWIFT, card — each with different validation and settlement logic.
    - E-Commerce: A shipping-calculator factory (FedEx / UPS / USPS) or a payment-gateway factory (Stripe / PayPal / Apple Pay) selected by carrier or method at checkout.
    - Health Insurance: A claim-processor factory keyed on claim type — medical, dental, vision, pharmacy — since each is adjudicated under different rules.
  - builder: constructs a complex object step by step with many optional fields, often immutable, via a fluent API.Lombok's @Builder already wraps this, so  rarely write it manually.
    - Banking: Assembling a loan-application object with many optional fields (collateral, co-signer, term, rate type, fees, escrow) without a giant telescoping constructor.
    - E-Commerce: Building an order object — line items, discounts, coupons, gift wrap, billing vs. shipping address, delivery options — where most fields are optional.
    - Health Insurance: Constructing a policy or claim object with optional riders, dependents, coverage tiers, and exclusions
  - proxy: a surrogate that controls access to a real object (access control, lazy loading, caching, or remote calls)
    - Banking: A protection/transaction proxy wrapping money-transfer methods — @Transactional (a proxy) guarantees atomicity, and an access-control proxy enforces role/authorization checks before a balance transfer executes.
    - E-Commerce: A caching proxy in front of the pricing or catalog service — serve cached results, fall through to the real service on a miss — or a virtual proxy lazy-loading product images and reviews.
    - Health Insurance: A protection proxy enforcing HIPAA access control on member PHI (only authorized roles can read records), often combined with an audit/logging proxy that records every access for compliance.

- what is microservice architecture
  It's an architectural style where a single application is decomposed into a set of small, independently deployable services.

- why microservice architecture
   
   - Easier horizontal scaling of the hot service
   - Failure isolation (if shipping is down, users can still log in and check exisitng orders)
   - Can deploy one service without taking the whoe system down. Different services can use different tech stacks and different eams.

   Cons:
   - Network unreliability
   - Producer/consumer overload
   - Potential data loss
   - Session consistency
   - Distributed configuration
   - Observability complexity

- microservice main components
  
  - API Gateway — the single entry point handling auth/identity, traffic routing, rate limiting, and load balancing.Implementations: Spring Cloud Gateway (Zuul is legacy), AWS API Gateway, Kong, Apigee.

  - Service Discovery / Registry — a registration center where each instance sends a periodic heartbeat; miss several and the instance is deregistered and its IP removed, so callers know they now have 19 instead of 20 instances. Implementation: Eureka 2.0, with Zookeeper or Nacos as alternatives.

  - Config Server + Vault — centralizes all configuration (DB URLs, timeouts, thread-pool sizes) instead of managing per-service application.properties, with credentials kept in a vault and referenced through encrypted variables so they never sit in plaintext.

  - Load balancer — distributes traffic across a service's instances; strategies include round-robin, geographically-closest, and lowest-latency. Client-side balancing was Ribbon (now in maintenance), with cloud/server-side options like AWS ALB.
  - Inter-service communication — synchronous via REST/Feign clients, and asynchronous messaging (Kafka, RabbitMQ) to absorb the producer/consumer overload problem — the message queue buffers a fast upstream so a slower downstream doesn't drop data.
  - Distributed tracing — a unique trace ID embedded in a request as it travels service → service → service, so you can follow one request across the cluster (plain AOP logging only covers a single app). Zipkin + Spring Cloud Sleuth was the classic combo; in Spring Boot 3.x, Sleuth is replaced by Micrometer Tracing.
  - Circuit breaker / resilience — graceful downgrade so a stuck endpoint redirects users to a friendly error page via a fallback handler instead of leaving them clicking a dead button. Resilience4j is the current library (Hystrix is deprecated).
  - Monitoring / observability — Actuator as the collector → Prometheus as the time-series database → Grafana as the dashboard; Spring Boot Admin for endpoints/logs/threads; and the ELK stack (Logstash → Elasticsearch → Kibana) for log aggregation and full-text search. On AWS: CloudWatch, CloudTrail.
  - Database-per-service — each service typically owns its own database for isolation, with a midnight batch job consolidating records into a data warehouse for the full-platform picture.
