- equals vs ==

  == compares references; Object.equals() also compares references unless overridden; override hashCode whenever you override equals.

- how to inject bean with same type

   Spring injects by type, so duplicates conflict → resolve with @Primary or @Qualifier (by name).

- oop 4 principles
  
  - encapsulation: via access keywords such as public, private, protected, default keyword
  - inheritance: interface and abstract class. interface supports multiple inheritance.
  - abstraction: abstract class and interface
  - polymorphism: overriding and overloading. overriding: run time polymorphism. happens in different classes. overloading: compile time polymorphism, happens in the same class. the same class signature.

- what is Executors library

  It's a utility class with factory methods for common pools (newFixedThreadPool, newCachedThreadPool, newSingleThreadExecutor); fixed vs cached differ in core pool size — cached has core size 0, so threads are created from the max pool when a task arrives. Should avoid using these factory methods — always customize a ThreadPoolExecutor with the 7 parameters yourself (core pool, max pool, keep-alive time, time unit, work queue, thread factory, rejection policy). Use sane (not huge) sizes and a bounded queue to avoid OOM.

- java 21 features

  Virtual threads are JVM-managed lightweight threads for high-throughput concurrency. Saves us from managing and recycling a fixed thread pool. In modern version of SpringBoot, we use virtual threads combined with Tomcat version that supports asynchrnous tasking to conduct some reactive programming.

- what is thread local

  A wrapper / "context window" that stores per-thread variables — values held independently for each thread. It avoids synchronization/blocking on a shared resource because each thread has its own copy.

- java version

  Java 21 — latest project; upgraded for Spring Boot 3.0 and swapped to virtual threads (no thread-pool config; GC recycles them).
  Java 17 — upgraded to support the first Spring Boot 3.0 release; record (immutable classes) and sealed (limited inheritance).
  Java 8 — used heavily: Optional (wrap return values in the DTO/DAO layer to prevent NPE), Stream API (parallel vs serial; each stream = intermediate ops + one terminal op like forEach/collect/reduce; intermediate ops take a functional interface + lambda, e.g. a predicate for filter), lambdas, functional interfaces, default methods.

- injection types

  DI is the implementation of IoC. Three types: constructor, field, setter. Since Spring Boot 2.0, always use constructor injection — prevents NPE, guarantees the bean exists at startup, easier to unit test (pass mocks). Circular dependency → @Lazy.

- have you used patch

  Yes — and PUT too. PUT updates the entire row of the record; PATCH updates only some columns in the same row. Partial update → PATCH; full-row update → PUT. PATCH is not idempotent. For a simple question like this, cut it short — don't burn the first 15 seconds wiggling.

- garbage collector

  GC is automatic — a guardian/daemon thread runs collection when the app boots, so you don't manually free memory (Java's edge over C/C++). Then: as a developer you can configure the collector via JVM args (-XX) — serial (small apps), parallel (multi-threaded), ZGC / Shenandoah (low-latency, large heap), Epsilon — chosen per scenario. Generations: young gen (recent objects) and old gen (long-lived). 

## Q&A 

- jdbc vs hibernate

  JDBC is the low-level standard API where you write SQL and map results by hand. In JDBC, we write the SQL and bind params with PreparedStatement, and manually map ResultSet → objects with a RowMapper.
  
  Hibernate is an ORM framework built on top that auto-generates SQL and auto-maps results:  annotate entities (@Entity, @Table, @Column) and it generates SQL and maps rows automatically.

  JDBC has heavier boilerplate but full control for complex queries in the case when there are big multi-table joins.

- Statement vs PreparedStatement vs CallableStatement

  Statement: static SQL built by string concatenation. No precompilation, no parameter binding, and vulnerable to SQL injection. Don't use it for dynamic input.
  
  PreparedStatement: precompiled SQL with ? placeholders and typed setters (setString, setInt). Prevents injection, caches the execution plan for repeated calls, and is the default choice.
  
  CallableStatement: extends PreparedStatement; used to call stored procedures/functions ({call my_proc(?, ?)}), and supports IN / OUT / INOUT parameters.

- how to prevent sql injection

  Never concatenate user input into SQL. Instead, bind it as a parameter so input stays data.

  Use PreparedStatement placeholders with typed setters; in ORM use bound JPQL params / named params / Criteria API, not string-built queries.

  Defense in depth: input validation / allow-lists, least-privilege DB accounts, escaping for dynamic identifiers (table/column names can't be parameterized), and don't leak raw DB errors.

- what is ORM

  Object-Relational Mapping is a framework that maps Java objects to relational tables so we can work with objects instead of writing SQL plus manual row mapping.

  It removes the RowMapper boilerplate, and adds annotations like dialects, caching, lazy loading etc.

- JPA vs Hibernate

  JPA is the standard interface and Hibernate is the most popular implemenation.

  JPA = Jakarta Persistence API (jakarta.persistence in Spring Boot 3, formerly javax). It defines the annotations (@Entity, @Id), EntityManager, and JPQL — but it's just a contract with no runtime of its own.

  Hibernate = a concrete ORM that implements JPA and adds features beyond the spec (native Session API, richer caching, extra fetch/mapping options).

  Stack is Spring Data JPA -> JPA -> Hibernate. 

  JPA is the interface, Hibernate is the class implementing it — same relationship as the JDBC API spec vs. a specific driver.

- what are the Persistent State in Entity LifeCycle

  - Transient (New): freshly new-ed, no DB identity, not attached to a persistence context — not saved.
  - Persistent (Managed): attached to the EntityManager/Session and tracked; changes are auto-flushed via dirty checking. Result of persist() or find().
  - Detached: was persistent, but the session closed or detach()/clear()/evict() was called; it keeps its identity but is no longer tracked — changes won't sync until merge().
  - Removed: marked for deletion by remove(); deleted on flush/commit.
  - Transitions: persist (transient→persistent), find (→persistent), commit/close (persistent→detached), merge (detached→persistent), remove (persistent→removed).

- Mapping relationship

  JPA maps table relationships with @OneToOne, @OneToMany, @ManyToOne, and @ManyToMany.

  @ManyToOne / @OneToMany: e.g., many Employees → one Department. @JoinColumn defines the foreign key on the owning side; @OneToMany(mappedBy = "department") marks the inverse side.
  @OneToOne: e.g., User ↔ Profile.
  @ManyToMany: uses a join table via @JoinTable; if the relationship carries its own attributes, model it as two @OneToManys to an explicit join entity instead.
  Owning side vs inverse side: the owning side holds the FK and controls persistence; mappedBy marks the inverse. Pair every relationship with a deliberate fetch type and cascade.

- what is the cascade type

  Cascade controls whether an operation on a parent entity propagates to its associated children.

  Types: PERSIST, MERGE, REMOVE, REFRESH, DETACH, and ALL.
  Example: @OneToMany(cascade = CascadeType.ALL) — saving or deleting the parent saves or deletes the children. Good for parent-owned children like Order → OrderItem.
  Caution: REMOVE / ALL can delete more than you intend — apply it only to truly owned children. orphanRemoval = true is related but distinct: it deletes a child once it's removed from the parent's collection.

- what is the fetch type

  Fetch type controls when a related entity is loaded — EAGER (immediately with the parent) or LAZY (on first access).

  Defaults: @ManyToOne / @OneToOne = EAGER; @OneToMany / @ManyToMany = LAZY.
  LAZY loads the association only when accessed — avoids pulling unneeded data, but risks a LazyInitializationException if the session is already closed.
  EAGER loads upfront — risks over-fetching and the N+1 query problem.
  Best practice: default to LAZY and fetch what you actually need explicitly with JOIN FETCH or an entity graph. N+1 is the standard follow-up question here.

- what is the first/second level cache

  L1 is per-session and on by default; L2 is shared across sessions and must be enabled.

  L1 (first-level): scoped to a single Session/EntityManager (the persistence context). Always on, can't be disabled. Fetch the same entity twice in one session and the second read comes from L1 — no second DB hit. Not shared between sessions.

  L2 (second-level): scoped to the SessionFactory and shared across all sessions; you must configure a provider (EhCache, Caffeine, Hazelcast). Best for read-mostly reference data — e.g., the top-10 best-sellers shown to every user during a sale.
  (There's also a separate query cache that caches query result IDs.)

- left join vs right join vs inner join vs outer join vs cross join

  INNER JOIN: only rows that match in both tables (the intersection).

  LEFT (OUTER) JOIN: all left rows plus matched right rows; unmatched right columns come back NULL.

  RIGHT (OUTER) JOIN: all right rows plus matched left rows; unmatched left columns come back NULL.

  FULL OUTER JOIN: all rows from both sides, NULLs where there's no match. MySQL has no native FULL OUTER — emulate it with LEFT  JOIN UNION RIGHT JOIN.

  CROSS JOIN: Cartesian product — every left row × every right row, with no join condition.

- union vs union all

  Both stack result sets vertically; UNION removes duplicates, UNION ALL keeps them.

  UNION runs a distinct/sort step to dedupe → slower.
  UNION ALL keeps every row, including duplicates → faster, no dedup overhead.
  Both require the same number of columns with compatible types across the queries.
  Use UNION ALL when you know there are no duplicates (or you want them) for better performance.
