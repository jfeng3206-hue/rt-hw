  1. Where did you use singleton in your project?

      For Singleton Design Pattern, I use it for things that are expensive to create and meant to be shared once — a database connection pool, a thread pool, or loading a wide, fixed reference table into memory once instead of recreating it on every request. For example, a reference table with hundreds of columns that's fixed at runtime — you load it once as a singleton rather than rebuilding it repeatedly. The reason is the same in all cases: one shared instance, created once, to avoid wasting resources.

  2. How to use stream to filter people younger than 30

      I take the list of people, call .stream(), use .filter() with a predicate — p -> p.getAge() < 30 — and then .collect(Collectors.toList()) as the terminal operation to get the list of people under 30

  3. How do you design RESTful APIs to get/create/update an object

      I design it in four parts. First the HTTP methods for the CRUD operations — GET to read, POST to create, PUT to update, DELETE to remove. Then the URL — and the URL never contains verbs; what it carries is path variables. After that I consider request parameters, headers, and the request body — especially the body for a POST, where I send the new record as JSON. Then the response: the response body carries the payload plus the HTTP status code, and the status codes have five levels — 100 informational, 200 success, 300 redirect, 400 client error, 500 server error.

  4. Write REST api (User and ToDoItem): many to many relationship, create api for CRUD operations

      This is still a RESTful endpoint design question, so I start the same way — clarify the requirement and declare the data before coding. For the many-to-many, I model it with two entities, User and Todo, joined by a @ManyToMany relationship in Spring Data JPA, which creates a join table; I'd expose DTOs rather than the entities directly. Then I design the CRUD endpoints — GET to read, POST to create, PUT to update, DELETE to delete — each going through the controller to the service to the repository layer. So the same design structure as before: HTTP methods, URL with path variables, request body for creates, and response body plus status code.

  5. What is SOLID principle

      SOLID is five principles for object-oriented design — it's basically the detailed implementation of good OOD. 
      Single Responsibility: a class should have one reason to change, one job. 
      Open/Closed: open for extension, closed for modification — in Java that means I extend behavior through inheritance or interfaces rather than editing existing code. 
      Liskov Substitution: a subtype is usable wherever its parent is — implemented through polymorphism, like a List reference holding an ArrayList or LinkedList. 
      Interface Segregation: keep interfaces small and focused rather than one huge interface that forces classes to implement methods they don't need. 
      Dependency Inversion — depend on abstractions, which is exactly the reasoning behind Spring's IoC, where the container injects dependencies instead of the developer wiring them manually.


**Q&A**

- Why spring boots? pros and cons

  SpringBoot automatically gives me three features
    - auto-configuration, which configures beans based on what's on the classpath; 
    - starter dependencies, which bundle compatible libraries so I don't fight version conflicts; 
    - an embedded Tomact server  so I run a single executable JAR instead of deploying a WAR to an external server. 
    - It also ships Actuator for production monitoring out of the box. 

- How to start a spring boot project from scratch?

  Generate the skeleton from Spring Initializr, choosing the build tool (Maven/Gradle), Java version, Spring Boot version, and the starter dependencies — typically spring-boot-starter-web, plus data-jpa and a DB driver if it's persistent. That gives me the pom.xml/build.gradle, the standard src/main/java + src/main/resources layout with application.properties, and the main class annotated @SpringBootApplication with a main that calls SpringApplication.run(...). From there I build out the layers — controller, service, DAO — and run with mvn spring-boot:run or by running the main class.

- @Controller vs @RestController

  @Controller is the classic MVC controller — methods return view names a ViewResolver renders to HTML. @RestController is @Controller + @ResponseBody, so every method's return value is serialized straight into the response body, normally JSON. For a REST backend I use @RestController so I don't annotate every method with @ResponseBody

- @PathVariable vs @RequestParam

  @PathVariable binds a value embedded in the URI path — /employees/{id}, where id is part of the resource identity. @RequestParam binds a value from the query string — /employees?status=active&page=2. So path variables identify which resource; query params filter, sort, or paginate it. @RequestParam also supports required=false and defaultValue, which fits optional filters.

- @RequestBody vs @ResponseBody

  @RequestBody deserializes the incoming request body into a Java object — typically a DTO on a POST/PUT. @ResponseBody serializes the Java object I return into the response body. With @RestController, @ResponseBody is already applied to every method, so I only write @RequestBody explicitly.

- how to use GetMapping, PutMapping, PostMapping, DeleteMapping, RequestMapping?

  @RequestMapping is the general-purpose one — it maps a URL to a handler and you specify the HTTP method with method = RequestMethod.GET. 
  
  The others — @GetMapping, @PostMapping, @PutMapping, @DeleteMapping — are shortcuts introduced in Spring 4.3 for the specific verbs, so @GetMapping("/x") is just @RequestMapping(value="/x", method=GET). I put a class-level @RequestMapping for the base path and method-level verb annotations for each endpoint, mapped to CRUD: GET reads, POST creates, PUT updates, DELETE removes.

- What is Spring Actuator?

  Actuator adds production-ready endpoints exposing the app's internal state over HTTP — /actuator/health, /metrics, /info, /beans, /env. Dependency is spring-boot-starter-actuator; expose endpoints with management.endpoints.web.exposure.include. It's the metric source that Prometheus scrapes and Grafana visualizes, bridged by Micrometer.

- how to achieve async in spring boot application

  For background work, I annotate a method @Async and enable it with @EnableAsync; the method runs on a separate thread pool and returns void or a CompletableFuture. 
  
  For composing parallel calls, I use CompletableFuture directly — supplyAsync to start, thenApply/thenCompose to chain, thenCombine to merge — so an endpoint needing three downstream calls fires them in parallel instead of sequentially.

- how does spring handle exception

  Centralized handling with @RestControllerAdvice + @ExceptionHandler methods — one place to catch exceptions across all controllers and return a consistent error body (message, timestamp, status). Custom domain exceptions map to the right status — ResourceNotFoundException → 404, validation failure → 400.

- how does spring validate data

  Bean Validation (JSR-380): annotations like @NotNull, @NotBlank, @Size, @Email, @Pattern on the request DTO, then @Valid on the @RequestBody to trigger it. On failure Spring throws MethodArgumentNotValidException, which I catch in @RestControllerAdvice to return a clean 400 with field errors. The backend never trusts the frontend to send clean data.

- how does spring do the log

  Spring Boot uses SLF4J as the facade and Logback as the default implementation. It is auto-configured. In code I get a logger via LoggerFactory.getLogger(MyClass.class) (or Lombok's @Slf4j) and log at levels: ERROR, WARN, INFO, DEBUG, TRACE. I control levels per package in application.properties with logging.level.com.myapp=DEBUG, set file output with logging.file.name, and for anything beyond that drop in a logback-spring.xml for custom patterns, rolling policies, or appenders.

- cache hit vs cache miss

  A cache hit is when requested data is already in the cache, so it's served fast without touching the slow source (database, remote API). A cache miss is when it's not there, so the app falls back to the source, returns the result, and usually writes it into the cache so the next request hits.

- do some research on Redis and have a basic understanding

  Redis is an in-memory key-value data store, most commonly used as a cache that sits in front of a database to serve hot data fast. Because it's in-memory it's extremely low-latency, sub-millisecond. What distinguishes it from a plain key-value cache is that values can be rich data structures — strings, hashes, lists, sets, sorted sets — so it's used well beyond caching: session storage, rate limiting (counters with expiry), leaderboards (sorted sets), pub/sub messaging, and distributed locks.

- @RestControllerAdvice instead of @ControllerAdvice

  @ControllerAdvice is the global exception/advice handler for MVC; its @ExceptionHandler methods would need @ResponseBody to return data instead of a view. @RestControllerAdvice is @ControllerAdvice + @ResponseBody, so the handler methods serialize their return value straight to the response body as JSON. For a REST API I use @RestControllerAdvice so my error responses come back as JSON error objects without annotating each handler.
