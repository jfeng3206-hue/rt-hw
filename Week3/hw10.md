- what is AOP
  AOP is a programming approach to break the normal serial execution order to inject cross-cutting logic, such as logging, exception handling, security, without duplicating code in every method.

- what is JointPoint and Aspect in AOP

  - Aspect: a module that encapsulates a cross-cutting concern. Use `@Component` + `@Aspect`

  - Joint Point: A point in program execution where advice can be applied. In Spring AOP it is always a method execution. The JoinPoint object passed into advice exposes the method signature, arguments, and target.

- what is pointcut, advice, target

  - Pointcut: A predicate/expression that selects which join points get advised - the "where".
    ```
      @Pointcut("execution(*.StudentServiceImpl.*(..))")
    ```

  - Advice: The action taken, plus its timing - the "when." Types: @Before, @After, @AfterReturning, @AfterThrowing, @Around (uses ProceedingJoinPoint.proceed())

- ApplicationContext vs BeanFactory

  ApplicationContext is a superset of BeanFactory, and in practice we always use ApplicationContext. 

  BeenFacotry is the root IoC container interface. ApplicationContext extends BeanFactory and adds the enterprise features, such as eager singleton instantiation at startup, auto-registration, event publishing, resource loading, AOP/annotation integration.

- How is Spring MVC Working Flow 

  1. Request arrives at `DispatcherServlet` (front controller)
  2. It consults `HandlerMapping` to find the matching handler and any interceptors
  3. The appropriate `HandlerAdapter` invokes that handler
  4. The controller then executes business logic (call service→DAO) and returns either a ModelAndView or a return object (REST)
  5. View-based: a `ViewResolver` resolves the logical view name to a concrete View, which renders the model into HTML
  6. If @RestController/@ReponseBody, no view resolution: an HttpMessageConverter serializes the return object straight to JSON/XML.
  7. `DispatcherServlet` writes the response back to the client.

- how does @Autowired work

  @Autowired tells Spring to resolve and inject a dependency from the container, matching primarily by type.

  Resolution order: by **type** first → if multiple candidates, narro by `@Primary`, then `@Qualifier`, then fall back to matching the field/parameter name to a bean name. If still ambiguous, `NoUniqueBeanDefinitionException`; if none found and required=true (the default) → `NoSuchBeanDefinitionException`.

  Injection points: constructor, setter, or field

  For optional dependencies: `@Autowired(required = false)`, or wrap in `Optional<T>`, or use `@Nullable`.

- @Autowired and @Qualifer

  @Autowired resolves by type, so when two or more beans of the same type exists, it can't decide and throws `NoUniqueBeanDefinitionException`. @Qualifier("beanName") helps Spring clear the confusion.

  You can also use `@Primary` making one bean as the default. Or use custom qualifier annotation. 


- 2 use cases for @PostConstruct and @PreDestroy

 - @PostConstruct: runs after dependency injection completes but before the bean serves requests
  1. Initialization that needs injected dependencies — work you can't do in the constructor because the dependencies aren't wired yet (e.g. validating config, pre-loading a cache or reference data using an injected repository).
  2. Warming up / starting resources — opening a connection pool, kicking off a scheduled/background task, or establishing a client connection once the bean is fully assembled.

- PreDestroy: runs before the bean is destroyed on container shutdown. Only fires for singleton on a normal container shutdown because Spring does not manage the full destruction lifecycle of prototype beans. 
  1. Releasing resources - closing DB connections, file handles, thread pools, or sockets to avoide leaks
  2. Graceful cleanup - flushing buffers/caches, persisting in-memory state, or deregistering/unsubscribing from a service registry or message queue.
